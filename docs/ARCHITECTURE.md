# Arquitetura

Um binário Rust oferece comandos separados `serve`, `import`, `import-public-report`, `collect`, `collect-vip`, `maintain` e `demo`. Uma API Axum/Tokio atende exclusivamente o SQLite local. Nenhuma consulta do consumidor chama supermercados. A API não depende das lojas para responder; os coletores precisam de rede. Não há login de consumidor, pagamentos ou telemetria.

O adaptador genérico `AuthorizedFeedAdapter` implementa `SourceAdapter` para CSV/JSON contratados. O adaptador de vitrine `vip` tem configuração independente e usa o bootstrap anônimo publicado pelos sites: identidade do domínio, sessão visitante, confirmação da filial/CD e paginação de todos os departamentos. Somente três filiais verificadas de Sorriso estão habilitadas. Protocolo e limites em [PUBLIC_CATALOGUES.md](PUBLIC_CATALOGUES.md). O serviço `sorriprecos-vip.service` mantém `collect-vip --watch`, com intervalo de 600 s por rede, concessão exclusiva no SQLite e `flock`. Sem sobreposição ou coleta disparada por busca.

Paginação aceita somente a mesma origem do feed. Redirects não são seguidos. As requisições têm timeout, tamanho máximo, retentativas limitadas e backoff. `Retry-After` longo encerra a execução para reagendamento, sem insistência. Coletas são sequenciais, inclusive entre lojas que compartilham domínio. O intervalo padrão por fonte é de 24 horas, com mínimo de dez minutos. O timer genérico verifica vencimentos a cada dez minutos, com até dez segundos de dispersão. O coletor de vitrine usa seu próprio loop de 15 s.

Cada página é uma transação atômica de até 10 mil linhas/8 MiB. Uma página inválida não altera os seus registros. Páginas anteriores válidas permanecem se uma página posterior falhar; o cursor HTTP não avança e a próxima execução pode reaplicá-las idempotentemente. Falha de rede não apaga ofertas. No coletor VipCommerce, somente após catálogo completo, SKUs ausentes ou não normalizáveis passam a disponibilidade desconhecida. Disponibilidade precisa ser informada explicitamente pela fonte.

SQLite usa WAL, chaves estrangeiras, busy timeout de 10 s, synchronous NORMAL e pool de quatro conexões. Índices atendem produto/filial/tempo. FTS5 normaliza acentos e a consulta usa termos prefixados, escapados pelo servidor, com paginação por ID. O importador mantém o índice FTS na mesma transação. Histórico grava somente mudanças de valores; manutenção elimina histórico anterior a 90 dias e execuções anteriores a 30 dias.

Preços usam inteiros em centavos. Produtos reais e DEMO têm identidades distintas. O menor preço considera dados disponíveis de até 48 horas e validade não expirada. Preço de clube/atacado nunca substitui o preço comum no ranking geral. A API expõe também condições, preço promocional, observação, origem e filial.

O aplicativo usa Kotlin Multiplatform, Compose, Ktor, Coroutines e Serialization. Interface, modelos, cliente, cache e regras de apresentação são compartilhados; Android utiliza CIO e SharedPreferences; iOS utiliza Darwin e NSUserDefaults. O cache guarda no máximo 60 respostas; favoritos são locais e limitados a 200 produtos. Consultas têm debounce de 350 ms e cancelamento; falha de conexão permite leitura do último resultado salvo, explicitamente marcado offline. Não há sincronização de favoritos com servidor.

O APK debug permite HTTP somente para loopback e o host do emulador. O teste autorizado nesta entrega utiliza exclusivamente celular físico via `adb reverse`; nenhuma porta é publicada na rede. Builds release exigem HTTPS. A configuração do endereço da API está acessível em Conexão.

A API limita 64 consultas concorrentes, 180 consultas/minuto por IP de conexão e até 50 resultados por página. O mapa de IPs tem limite de memória. ETag, Cache-Control de 30 s e gzip reduzem transferência. Atrás do Caddy, o IP da conexão é o proxy; o limite passa a ser compartilhado. Não se confia automaticamente em X-Forwarded-For enviado pelo cliente. Para lançamento, dimensionar o limite total conforme os benchmarks e implementar limitação no proxy se necessário.

iOS está preparado para aparelho arm64 e simulador Apple Silicon. Compose 1.11 não oferece o antigo target Intel x64 utilizado em versões anteriores. Não houve compilação iOS em Linux.

Um caminho independente em Python extrai o relatório público Procon-MT de março de 2026 e gera lotes JSON por rede. O filtro exige município, UF, nome e endereço/número mapeados; o importador Rust exige município/UF também em toda linha real. `import-public-report` conserva a proveniência pública sem classificar a fonte como feed varejista autorizado. O snapshot tem 27 produtos/31 observações, em sete redes/oito filiais; não fornece preços atuais. A API expõe referência histórica separada do menor preço recente, e o app apresenta avisos explícitos. O levantamento tem 26 redes e 29 referências de filiais, uma inativa; não representa censo de lojas operantes.

A interface compartilha os componentes de marca/ícones vetoriais, miniaturas genéricas, navegação e comparação no código comum. A aparência padrão é clara; alto contraste e escala adicional de fonte são preferências locais. Android ajusta os ícones das barras do sistema por uma função de plataforma; iOS conserva o controle do UIViewController. Não foi adicionada dependência de imagens remotas ou biblioteca de gráficos. A referência de UI não alterou a proveniência, frescor ou regras de elegibilidade dos preços.

`source_products.source_kind` separa `retail` de `public_report` nas consultas e agregações. `source_catalog_items` guarda todos os itens públicos recebidos e o motivo de revisão, mesmo quando não entram na comparação. `catalogue_collectors` registra intervalo, execução e volumes sem guardar a sessão. Cache do aplicativo inclui o modo histórico e foi versionado para não reapresentar respostas antigas do Procon como catálogo atual.
